Bad Case 处理

从现象到根因的工程判断，每个问题都有针对性解法而不是绕过

01
LLM 不遵循指令格式
⚠ 问题
7B 模型忽略 system prompt 中的操作词表，对"39-49小节空白帮我加鼓"自行发明 {"bar_39":[{"time":"b39.00","note":"Kick"}]} 格式，无法被系统解析执行
✓ 解决
引入规则优先引擎：正则匹配"N-M小节 + 空白/加鼓"模式，直接构造 fill_drums_pattern 操作绕过 LLM 调用，延迟从 5-8s 降至 <1ms
02
BPM 估算 2× 误差
⚠ 问题
pretty_midi 的 estimate_tempo() 对 EDM 四四拍 Kick 鼓型估算始终是真实 BPM 的 2 倍（128BPM 返回 256），导致生成的节拍与用户预期完全错误
✓ 解决
改用 get_tempo_changes()[1][0] 直接读取 MIDI 文件头中的 tempo 事件，获取 μs/beat 精确值换算，完全绕开信号估算
03
Ableton API 命令边界未知
⚠ 问题
代码调用了 get_tempo / load_drum_rack 等命令，但 Ableton Remote Script 仅支持有限命令集，社区版命令边界没有官方文档，运行时才发现报错
✓ 解决
逐一测试可用命令集，建立白名单并实现能力降级机制：不支持的命令 best-effort 跳过并记录日志，不阻断主流程
04
Prompt 花括号语法冲突
⚠ 问题
LangGraph prompt 内嵌 JSON schema 示例（如 {"op":"transpose"}），Python str.format() 将 {} 解析为变量占位符，导致 KeyError 崩溃
✓ 解决
全面排查并将 prompt 中的 JSON 示例花括号统一改为 {{}} 双重转义，intent / plan / reflect 三个核心节点全部修复
05
进程重启丢失轨道状态
⚠ 问题
Ableton Bridge 重启后，内存中的 track_state 清零，已生成的 1306 条 DRUMS 音符数据全部丢失，后续编辑指令无法执行
✓ 解决
设计 JSON 磁盘持久化层（data/bridge_state.json），每次注入 Ableton 后同步写盘，启动时自动加载，实现无感热重启
06
Clip 边界截断音符
⚠ 问题
填充 bars 39-49 对应 beats 152-196，超出 clip 默认 32 beat 长度，注入时被 Ableton 静默丢弃，实际 DAW 中无声无息
✓ 解决
注入前计算 required_len = max(start + duration)，若超出当前 clip 长度则先调用 set_clip_length 扩容，再执行音符注入
